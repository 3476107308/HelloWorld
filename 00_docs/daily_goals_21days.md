| 8 | 能口头讲清 6 个问题（见下） | 自述 / 面试模拟 |

**必须能回答的 6 个问题**（这才是"面试能讲清楚"）：

1. 为什么接收必须在独立线程？在 UI 线程直接读会怎样？
2. 线程间怎么把数据安全交给 UI？为什么不直接在子线程里 `setText`？
3. 粘包和半包分别是什么？你的分包算法时间复杂度是多少？
4. 曲线为什么要限长？无限追加会发生什么？
5. 你的协议里，一条消息的边界是怎么定的？为什么这么定？

## 3. 硬件与环境的真实现状（已核实）

| 项目 | 现状 | 对本计划的影响 |
|---|---|---|
| Qt 6.11.0（MinGW 64） | 有 `Qt6Network` / `Qt6Sql` / `Qt6Charts` | TCP 环回验收**立刻可用**，不依赖任何外部安装 |
| Qt SerialPort 模块 | **未安装**（`mingw_64` 下无 `Qt6SerialPort`） | **串口不能放关键路径**。代码写成抽象接口，串口实现可延后；需要时用 `C:\Qt\MaintenanceTool.exe` 补装 "Qt Serial Port" |
| 串口硬件 | **没有**（预算 300–500 元，随时可买） | 不是前置条件。虚拟串口 / TCP 足够验收；买硬件是加分项，放到 10/3 之后再决定 |
| 开发机 | Windows + `C:\Qt\Tools\mingw1310_64`；另有 VMware Ubuntu | 主战场 Windows（Qt Creator）；Ubuntu 只用来验证跨平台构建 |

**关于硬件，明确结论**：现在**不买**。理由：`QSerialPort` 的接口与 TCP 在"字节流"层面等价，先用 TCP + 虚拟串口把收发、线程、分包、曲线全部跑通；软件通了以后，10–40 元的 CH340/CP2102 模块插上就能用，那时才是它的价值最高点。**先买硬件再写代码，等于用硬件的不确定性替代码的不确定性背锅。**

## 4. 每日卡片制度（这是解决"没目标、没负罪感"的核心机制）

### 4.1 每张卡长什么样

`04_projects/device_monitor/DAILY_CARDS.md` 里，每天一张卡，**按日期排**（9月17日 → 10月7日），固定 7 个字段：

```text
Day N ｜ 9月XX日（周X）｜ 预计 Xh ｜ 阶段 P?

【今天唯一目标】一句话，只能有一个。

【三层拆解】            ← 按你已有的三层教学法
  ① 数据对象：今天要新增/修改哪个结构体、哪个成员？
  ② 业务逻辑：算法/流程是什么（先写成中文步骤）？
  ③ 文件/声明：动哪些文件、加哪些函数声明？

【验收标准】可执行、可观察。例如：
  - 命令：cmake --build build-windows-qt -j2
  - 现象：窗口标题出现 "rx: 12345 B"
  - 自测：故意发半条 JSON，程序不崩，日志出现 "parse failed"

【最低可交付】即使时间被砍，也必须做完这一条（通常是能编译 + 能跑）
【卡住怎么办】按顺序做这三件事，超 30 分钟就停下来记录问题
【提交】git add/commit 的一句话信息
【复盘 1 行】今天卡在哪 / 学到什么（写进 00_docs/daily_progress.md）
```

### 4.2 验收的三种证据（缺一不算完成）

1. **编译证据**：构建命令 + 无错误输出（可以截图或粘贴最后几行）。
2. **运行证据**：可观察的现象（数字变了、曲线动了、日志出现了某一行）。
3. **解释证据**：用 2–3 句话回答卡片里的"回答我"问题，**不许照抄注释**。

### 4.3 熔断规则（你选的："必须当天补回来，不准拖"）

既然选了最严格的规则，就必须配三个**防崩机制**，否则规则会在第 4 天失效：

**机制 A：每天有"最低可交付"**
卡片里那条"最低可交付"是当天的及格线。哪怕只剩 40 分钟，也**先把这一条做完**（通常是能编译能跑）。**做了 40 分钟的最低可交付，也算今天打卡成功**——这是防止"0 分日"的唯一方式。

**机制 B：欠账必须当天还，但允许"降级偿还"**
没做完当天任务时：

| 情形 | 处理 |
|---|---|
| 只欠"完善/优化"部分 | 记入 `daily_progress.md` 的"欠账"，从当天起 48 小时内补 |
| 欠"核心功能"部分 | **次日先还债再开新卡**，新卡整体后移 |
| 连续 2 天欠账 | 触发**降级**：当周任务砍掉一项非核心功能（记录进"砍掉的清单"） |

**机制 C：砍功能比拖日期优先**
进度落后时**永远优先砍功能，不动验收日期**。10/7 是硬边界（10/8 开学）。可砍顺序（从先砍到后砍）：

1. 多语言 / 编码转换（UTF-16、GB2312 等）
2. 数据回放
3. 拖拽缩放曲线的交互细节
4. 连接参数保存与多套配置
5. 最后一个才砍"性能实测数据"

**明确不砍**：多线程收发、UI 不卡、粘包/半包、README、演示录屏。这五个是简历和面试的全部价值。

### 4.4 每天的分段任务必须当天写
`DAILY_CARDS.md` 里 9月21日 之后的卡是**骨架**（目标 + 交付物 + 验收），**具体实现步骤在当天开始时现场细化**。原因：进度一定会偏，提前把 13 天写死只会得到一份你需要不断违背的计划。每周日（9/20、9/27、10/4）我会根据你实际完成情况重排下一周的卡。

**日期不后移，Day 编号才后移。** 任务卡以日期为主键：某天没做完，欠的任务仍挂在那个日期下面，不会顺延到下一个日期——这样"哪一天欠了什么"永远一眼可见。进度落后时砍功能（见 4.3 节），结束日期恒为 10月7日。

## 5. 每天的投入方式（3 小时版 / 7 小时版）

**在校日（3h）—— 拆成 "1 + 2"：**

| 时段 | 时长 | 做什么 |
|---|---|---|
| 第 1 块 | 40 min | 读 + 写：看卡片的三层拆解，先把"今天要动的文件/函数"写下来，再动手 |
| 第 2 块 | 100 min | 主攻：写代码、编译、调试（手机静音、不开视频） |
| 第 3 块 | 40 min | 验收 + 复盘：跑验收标准、commit、写 1 行复盘 |

**假期日（6–7h）—— 拆成 "2 + 3 + 1.5"：**

| 时段 | 时长 | 做什么 |
|---|---|---|
| 上午 | 2h | 新知识 + 骨架（今天要用的新类/新机制） |
| 下午 | 3h | 实现 + 调试（主体） |
| 晚上 | 1.5h | 性能实测 / 验收 / commit / 复盘 / 次日卡片细化 |

**关键纪律：不看"教学视频"度过主攻时段。** 视频只能放在上午块，且必须当天用代码验证。这个项目最大的风险不是难度，是"看了一下午视频，晚上发现什么都没写"。

## 6. 技术方案（决定每天任务怎么排）

```text
┌─────────────────────────────────────────────┐
│ UI 线程                                      │
│  ConnectBar（连接参数 + 打开/关闭）           │
│  DataView（收发框：文本 / HEX）               │
│  PlotView（自绘曲线，环形缓冲）                │
└───────────────┬─────────────────────────────┘
                │ 只传「一批字节 / 一批解析结果」（跨线程信号槽，队列连接）
┌───────────────┴─────────────────────────────┐
│ IO 线程（Worker，moveToThread）               │
│  Transport（抽象接口）                        │
│    ├─ TcpTransport   （QTcpSocket，先做）     │
│    ├─ SerialTransport（QSerialPort，后做）    │
│    └─ LoopbackTransport（自测用）             │
│  Framer（分包：行/超时/长度三种模式）           │
│  Decoder（字节 → 数值序列）                    │
└─────────────────────────────────────────────┘
```

**为什么这样切**（也是面试要讲的）：
- `Transport` 抽象让"换传输方式不改上层"——这正是 `docs/protocol.md` 里已经写下的"消息格式与传输方式无关"。
- IO 线程只做"收字节 + 分包 + 解码"，**绝不做画图**；UI 线程只做"显示 + 画图"。这就是 SerialTest 的 "UI update is separated from Data reception"。
- 曲线用**环形缓冲 + 限长**，不是无限 `append`。

**与现有代码的关系**：`DeviceListModel`、`TempChartWidget`、配置读写、`MessageParser` 全部保留并复用。`MessageParser` 的 `handleline` 拼写和 `pending_` 未接线的问题，在 Day 1 收口。
