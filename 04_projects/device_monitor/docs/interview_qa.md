## Q1 为什么接收必须在独立线程？在 UI 线程直接读会怎样？

### 一句话答案
`QTcpSocket` 本身是异步的、**单看 socket 并不会阻塞 UI** —— 真正会压垮主线程的是「**收到数据之后要干的活**」：解析、格式化日志、写文件、重排文本。我们把这些连 I/O 一起移到工作线程，主线程就只剩下画界面。

### 展开

**先纠正一个常见误答**："socket 会阻塞所以必须开线程" —— 对 `QTcpSocket` **不成立**。它是事件驱动的：`connectToHost` 异步、`readyRead` 由事件循环派发、`readAll` 不阻塞。所以单纯"接收"放在主线程也不会卡。

**真正的理由分三层：**

1. **处理成本**
   100 KB/s = 每秒约 100 条消息。每条消息在主线程要做：切分缓冲区 → `QJsonDocument::fromJson` → 格式化一条日志字符串 → 追加到日志控件 → 打开/追加/关闭 `run.log`。
   **这个项目里我们实测到过它的代价**：日志控件无上限时（`QTextEdit`，10673 行 / 5.4 MB），横向拖动分栏线会明显卡顿 —— 根因就是**主线程在做文本重排版**。修复后内存从 269 MB 降到 49 MB、卡顿消失、主线程 CPU **0.1%**。

2. **未来必然出现的阻塞 API**
   一旦接真实串口（`QSerialPort::waitForReadyRead`）、加 TLS 握手、或做同步大包解析，就**真的**会阻塞。到时候再改架构，代价比现在大得多。**现在隔离，是给未来留位置。**

3. **职责单一**
   主线程的唯一职责是"画界面和响应用户"。把 I/O 和解析放进去，等于让 UI 线程兼职做数据搬运 —— 任何一处变慢都直接表现为界面卡。

**实测证据**：`qDebug() << QThread::currentThread()` 打出两个不同的地址 —— `UI thread = QThread(0x…362e0, "Qt mainThread")`、`IoWorker::start thread = QThread(0x…97d60)`。

## Q2 线程间怎么把数据安全交给 UI？为什么不直接在子线程里 `setText`？

### 一句话答案
用**信号槽 + 队列连接**：Qt 把信号参数**拷贝一份**放进接收者线程的事件队列，在接收者线程里执行。**不能**在子线程直接 `setText`，因为 QWidget 不是线程安全的，且绑定在创建它的线程上 —— 那样做是未定义行为。

### 展开

**传递链条**：

```
IoWorker（io 线程）
  emit dataReceived(data)
      ↓  Qt 检查：发送者线程 ≠ 接收者线程
      ↓  自动选用 Qt::QueuedConnection
  data 被拷贝进 UI 线程的事件队列
      ↓
MainWindow 的 lambda 在 UI 线程执行
  writeLog / data_view_->appendData / parser_->appendData
```

**关键在 `connect` 的第三个参数**：

```cpp
connect(worker_, &IoWorker::dataReceived, this, [this](const QByteArray& data){
//                                        ↑
//                                 接收者上下文
});
```

这个 `this`（`MainWindow`）同时决定了两件事：

| 作用 | 说明 |
|---|---|
| **在哪个线程执行** | lambda 跟着接收者走 → UI 线程 → 里面动控件才安全 |
| **连接的生命周期** | `MainWindow` 析构时连接自动断开，不会调用已销毁的对象 |

**为什么不能直接 `setText`**：`QWidget` 及其子类不是线程安全的。它们内部有大量非原子状态（布局、重绘区域、焦点、样式缓存）。从别的线程调用会**偶发地**破坏这些状态 —— 而且往往**不报错、不一定崩**，只在压力大或时机巧合时崩。这类 bug 极难复现。

**顺带的收益**：因为"数据写入"和"读取"都在 UI 线程（`messageReceived` 的 lambda 在 UI 线程，`exportCsv()` 也在 UI 线程），`history_` 这个容器**完全不需要加锁**。这是同一个 `this` 带来的第二个好处。

## Q3 粘包和半包分别是什么？你的分包算法时间复杂度是多少？

### 一句话答案
TCP 是**字节流**，没有消息边界 —— 一次 `send` 不等于一次 `recv`。多条消息挤在一次读取里叫**粘包**，一条消息被拆到多次读取里叫**半包**。我的算法是"缓冲区 + 按 `\n` 循环切分"，单次到达 O(n)，但 `remove(0,…)` 的实现让最坏情况退化到 O(k·n)。

### 展开

**算法（`JsonLineParser::appendData`）**：

```cpp
buffer_ += data;                          // ① 新字节接到缓冲区尾部
while (buffer_.contains('\n')) {          // ② 只要还有换行
    int pos = buffer_.indexOf('\n');
    QByteArray line = buffer_.left(pos);  // ③ 切出换行前的一段 = 一条完整消息
    buffer_.remove(0, pos + 1);           // ④ 从缓冲区删掉它（含换行）
    parse(line);                          // ⑤ 解析
}
// ⑥ 没有换行的尾巴留在 buffer_ 里，等下一批数据
```

**复杂度分析（诚实版）**：

| 步骤 | 成本 |
|---|---|
| 找到 `\n`（`indexOf`） | O(n) |
| 取出这一段（`left`） | O(消息长度) |
| **`remove(0, pos+1)`** | **O(剩余字节数)** —— 底层是 `memmove`，要把后面的字节整体前移 |
| `parse` | O(消息长度) |

- **典型情况**：一次到达 n 字节、含 k 条消息，总成本 O(k·n)
- **最坏情况**：一次到达 1 MB、含 1000 条消息 → 每次 `remove` 都要搬移剩余部分 → 约 **500 MB 的 memmove**

**这个实现在 100 KB/s（1024 B 消息）下没有暴露问题**，因为一次 `readyRead` 通常只含几条消息。但如果吞吐再高一个数量级，**这里会是第一个热点**。

**更好的做法**（知道但没做）：维护一个**读游标**而不是真的删除 —— `readPos_` 往前移，只在缓冲区过半时才 `compact()` 一次。复杂度变成真正的 O(n)。

**5 个对抗性测试用例（已实测通过）**：

| 用例 | 网线上做了什么 | 结果 |
|---|---|---|
| SPLIT（半包） | 一条 JSON 分两段写，间隔 600 ms | ✅ 1 条 |
| STICKY（粘包） | 3 条 JSON 挤进一次 `Write()` | ✅ 3 条，顺序正确 |
| BYTE-WISE | 一条 JSON 拆成 40 次单字节写 | ✅ 1 条，只在 `\n` 到齐后出现 |
| MIXED | 一次写 = 上条尾 + 完整一条 + 下条头 | ✅ 3 条，顺序正确 |
| RECOVERY | 先发非法文本，再发合法 JSON | ✅ 1 条失败 + 1 条成功，坏数据不污染后续 |

## Q4 曲线为什么要限长？无限追加会发生什么？

### 一句话答案
不限长会有两个后果：**内存线性增长**，以及**每帧绘制成本随数据量增长**（`drawPolyline` 的点数是 O(n)）—— 表现为"越画越卡"。限长（`kMaxPoints = 60`）之后，两个成本都变成常数。

### 展开

**代码**：

```cpp
void TempChartWidget::addValue(double v)
{
    points_.append(v);
    while (points_.size() > kMaxPoints) {
        points_.removeFirst();      // 满了扔掉最老的
    }
    update();                       // 请求重绘（不是立刻画）
}
```

**不限长的两个后果：**

| 后果 | 机制 |
|---|---|
| **内存线性增长** | `QVector<double>` 只增不减，100 条/秒 → 一小时 36 万个点 ≈ 2.9 MB，跑一天就是 70 MB |
| **每帧成本线性增长** | `paintEvent` 里 `drawPolyline` 要遍历全部点；而且点越多，每个点占的横向像素越少，最后挤成一团黑 |

**限长还带来一个语义上的好处**：X 轴变成一个**固定的时间窗** —— 新点从右边进来，旧点从左边出去，曲线像传送带一样向左流动。这也是 X 坐标写成 `i / (kMaxPoints - 1)` 而不是 `i / (size() - 1)` 的原因：**否则每来一个新点，整条曲线都会横向抖一下。**

**这个项目里我们真的踩过同类的坑**：日志控件没有任何行数上限，涨到 **10673 行 / 5.4 MB**，内存 **269 MB**，横向拖动分栏时明显卡顿。改成 `QPlainTextEdit` + `setMaximumBlockCount(500)` 之后 → **49 MB、卡顿消失**。

> ⚠️ `setMaximumBlockCount` **只有 `QPlainTextEdit` 有**，`QTextEdit` 没有。这是当时选错控件的原因。

**已知不足**：`kMaxPoints = 60` 是按 1 Hz 采样设计的（= 60 秒时间窗）。在我们 100 条/秒的压测下，窗口只有 0.6 秒 —— 曲线滚得飞快。**采样率与窗口长度应该做成可配置的。**

## Q5 你的协议里，一条消息的边界是怎么定的？为什么这么定？

### 一句话答案
用 **`\n`（换行符）作为消息边界**，payload 是紧凑 JSON（`QJsonDocument::Compact`，内部不含裸换行）。选它是因为**可读、实现简单、坏数据自隔离、且兼容 `\r\n`**。

### 展开

**协议格式**（详见 `docs/protocol.md`）：

```
{"id":"1","temperature":37,"voltage":3}\n
{"id":"2","temperature":41,"voltage":3}\n
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | ✅ | 设备标识 |
| `temperature` | ✅ | 温度 |
| `voltage` | ✅ | 电压 |
| `online` / `ts` | ⬜ | 可选 |

**为什么用换行符定边界：**

| 理由 | 说明 |
|---|---|
| **可读** | 用串口助手/抓包工具直接能看懂 —— 调试工具的**第一诉求** |
| **实现简单** | 一个 `while(indexOf('\n'))` 就够，不需要状态机 |
| **坏数据自隔离** | 一条损坏的消息最多污染一行，下一行的 `\n` 就能重新同步。**不会因为一个字节错位而全盘错乱** |
| **兼容 CRLF** | 对端若发 `\r\n`，切出来的行尾多个 `\r` —— JSON 允许尾部空白，照样解析成功 |
| **JSON 天然安全** | 字符串里的换行在 JSON 规范里**必须**转义成 `\n`（两个字符），所以 payload 内不会出现真实换行，边界不会歧义 |

**代价与替代方案的取舍：**

| 方案 | 优点 | 缺点 | 为什么没选 |
|---|---|---|---|
| **Line（`\n`）** ✅ | 可读、自同步、实现简单 | 不可传二进制；多一次扫描 | **调试工具首选** |
| `LengthPrefix`（4 字节长度头） | 高效、支持二进制、一次定位 | 不可读；长度字段坏了就无法恢复 | 更像二进制协议，不适合人工调试 |
| 定长 | 最好解析 | 不灵活，短消息浪费带宽 | 设备协议不固定成定长 |

> **另一个必须知道的点**：解析失败**不能中断**。我们的实现是"丢这一条 + 发 `parseFailed` 信号记日志 + 继续处理后面的消息"。实测：先发一行垃圾文本再发合法 JSON，结果是 **1 条解析失败 + 1 条正常解析**，坏数据没有毒死解析器。

## Q6 如果波特率提高 10 倍，你的程序最先撑不住的是哪一层？

### 一句话答案
**最先撑不住的是主线程上"每条消息都要做的字符串与文件操作"** —— 具体是 `writeLog` 里**每条消息 open/append/close 一次 `run.log`**。网络 I/O 反而是最不容易出问题的部分（它在工作线程，而且我们实测到 100 KB/s 时**零背压**）。

### 展开

**把 10 倍负载下的各层成本排个序：**

| 优先级 | 层 | 会发生什么 | 现状 |
|---|---|---|---|
| 🔴 **最先崩** | `MainWindow::writeLog` | 每条消息打开一次文件 → 10 倍负载 = 每秒上千次 `CreateFile`/`CloseHandle` → 主线程被磁盘 I/O 占满 | **已知，未修** |
| 🔴 **紧随其后** | 日志控件的追加与重排 | 即使有 500 行上限，每秒追加几千行仍要频繁重绘 | 已限长，但仍受控于追加频率 |
| 🟠 第三 | `JsonLineParser::remove(0,…)` | 大批量到达时 O(k·n) 的 `memmove`（见 Q3） | 已知理论热点，100 KB/s 下未暴露 |
| 🟠 第四 | `MainWindow` 的解析 + 格式化 | 解析和字符串格式化都挤在 UI 线程 | 单点，但成本可控 |
| 🟡 第五 | 曲线 `addValue` | 每个点一次 `update()`；Qt 会合并重绘，成本有限 | 有 500 点上限思路，当前 60 点 |
| 🟢 **最后** | 网络 I/O / `QTcpSocket` | 在工作线程，写满时 TCP 自动背压 | **实测 100 KB/s 零背压** |

**"零背压"这个实测数据说明了什么**：发送端的速率全程稳定在 99.4–100.0 KB/s，**一次都没被拖慢**。这说明接收侧从来没有积压到把 socket 缓冲区填满 —— 也就是说，**当前负载下瓶颈根本不在网络层**。

**改进方向（按性价比排序）：**

1. **日志批量写**：把 `QFile` 作为成员保持常开，或攒够 N 条/每 100 ms 刷一次盘 —— 收益最大，改动最小
2. **日志限频**：收到 M 条只记一条，或在 UI 上做"每秒 N 条"的合并显示
3. **解析移出 UI 线程**：在 `IoWorker` 里就把 JSON 解析成结构体，信号传结构体而不是裸字节 —— 但这会把 `Transport` 抽象和协议耦合，需要权衡
4. **分包改读游标**：消除 `memmove`（见 Q3）

**这个问题的意义**：它逼你说出"**我的架构哪里是单点**"。答"网络会先崩"是错的 —— 实测数据摆在那里；答"主线程的日志 I/O 会先崩"才说明你真的分析过自己的代码。
